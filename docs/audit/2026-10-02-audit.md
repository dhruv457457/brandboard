# Patched audit — 2026-10-02

Scope: the whole repo, against `AGENTS.md`, `docs/SPEC-v2.md`, `docs/design-system.md`, `docs/TESTING.md` and `docs/privy-winners-research.md`.

**How it was done, and what it can't tell you.** Static review of all 27 API routes, `lib/**`, `components/**`, `packages/ai`, `packages/shared`, `middleware.ts` and the Privy code; the existing Playwright page suite run on a dev server; a click-through of the public pages in the browser pane at 1440 and 375 wide, light and dark; the benchmark `token2049.vanshu.fun` opened for comparison.
**Not done:** no signed-in flow was driven. Signing in goes through Privy (an outside identity provider), so I did not enter credentials; signed-in screens, on-chain flows, subdomains, and anything on mainnet are code review only. They are marked as such below.

## Summary

Fix before Oct 14, in this order:

1. **Open admin is a money risk if it stays on past the demo.** With `OPEN_ADMIN=true`, any signed-in person can `fastTrack` a milestone (skips the brand's dispute window) and `resolveDispute` (can pay the creator 100%). Also lets anyone rewrite any event page. Confirm it is `false` wherever real USDC is used, and flip it off after judging. (H1)
2. **Local UI tests fail on `localhost:3100`.** Privy's allowed-domain list has `3000` and `3200` but not `3100`, and `launch.json` and `playwright.config.ts` both default to `3100`. Every test I let run there failed on a Privy CSP error; on `3000`, 27 of 28 pass (1 skipped on purpose). Sign-in can't work on `3100` either. (H2)
3. **Judges have no way in.** The README has no "Try it" section and no test login. Privy test accounts exist for the e2e suite but are not offered to judges. (H3)
4. **Event creation was two steps with no cover. Fixed (Part B).** One flow now, a real cover uploader, live preview, a designed header and a designed fallback. (see Part B)
5. **`/e/<number>` pages had no app frame. Fixed.** An event with no slug links to `/e/12`, and `isListingPage()` read that as creator "e"'s listing. (F1)
6. **Ten API routes crash with a 500 on a malformed JSON body**, and the AI spend guards are weaker than they look (back-view generation is unlimited; limits are per server instance). (M1, M2)
7. **A creator can replace proof files after submitting them on-chain.** (M3)
8. **Docs disagree with the code in about ten places**, mostly about Privy signers, wallet export, nav, routes and mock mode. A judge reading `AGENTS.md` or `SPEC.md` is told things that are no longer true. (Doc drift)
9. **Reduced motion is only half covered.** CSS animation is handled globally; the `motion` library animations in Explore and the campaign builder are not. (M5)

## Findings

### [HIGH] H1. Open admin lets any signed-in user settle money steps and edit any event
- Area: api / privy
- Where: `apps/web/src/app/api/admin/act/route.ts:12` (`OPEN_FNS` includes `fastTrack`, `resolveDispute`, `createEvent`, `setEventActive`); `apps/web/src/app/api/events/[id]/route.ts` (any signed-in user may PATCH when `OPEN_ADMIN=true`).
- What happens: with `OPEN_ADMIN=true`, a creator submits proof, then calls `fastTrack` on their own milestone. The brand's review window is skipped and the keeper can release payment. Any person can also call `resolveDispute(..., 10_000)` and pay the creator in full. Any person can change another event's cover, links and slug. The Privy policy limits *which functions* are callable, not *who* may call them.
- Expected: fine on testnet for a demo (it is documented in the README and the console banner). Not fine with real USDC.
- Fix: S. Confirm `OPEN_ADMIN` and `NEXT_PUBLIC_OPEN_ADMIN` are `false` in the mainnet deploy (they are two separate variables and must match). For the testnet demo, consider limiting `fastTrack` and `resolveDispute` to listings the caller is not the creator of, and rate-limit `/api/events/[id]`.

### [HIGH] H2. Local tests and sign-in don't work on `localhost:3100`
- Area: tests / docs
- Where: `.claude/launch.json` (`web` uses `-p 3100`), `apps/web/playwright.config.ts` (default `baseURL` is `3100`), `docs/TESTING.md` §0 (lists `3000`).
- What happens: Privy's login frame answers with `frame-ancestors 'self' http://localhost:3200 … http://localhost:3000 …`, so `3100` is blocked: console error plus a 403, and `expectClean` fails every page test. The two tests I let run on `3100` both failed on exactly that. On `3000` the same suite gives 27 passed, 1 skipped.
- Fix: S. Either add `http://localhost:3100` to Privy's allowed domains (dashboard, not done here), or change the default to `3000`. I added a `web-3000` entry to `.claude/launch.json` (uncommitted, see Part B).

### [HIGH] H3. No judge instructions
- Area: docs
- Where: `README.md` (no "Try it"), `docs/TESTING.md` (a manual checklist for the team, not for judges).
- What happens: the hackathon criteria ask for a live link with access instructions and test login. A Privy test account exists (README line 126) but isn't offered.
- Fix: S. Add a short "Try it in 2 minutes" section: live URL, the test login, the faucet link, and the three clicks that show Privy (sign in, bid with no gas prompt, auto-bid).

### [MEDIUM] M1. Ten routes return a 500 on a malformed JSON body
- Area: api
- Where: `await req.json()` with no `.catch` in `api/ai/canvas/route.ts:16`, `ai/car-view:17`, `ai/layout:12`, `ai/model-shot:16`, `ai/styles:12`, `campaigns/route.ts:19`, `campaigns/[id]/route.ts:20`, `listings/metadata/route.ts:44` (inside a try, so it returns 400), `profile/route.ts:72`, `proofs/route.ts:17`.
- What happens: a bad or empty body throws, Next returns a bare 500, and the client shows a generic error. (`api/events/[id]` had the same issue; fixed in Part B.)
- Fix: S. `await req.json().catch(() => ({}))`, as `offers`, `autobid` and `notifications` already do.

### [MEDIUM] M2. AI spend guards are weaker than they look
- Area: api
- Where: `api/ai/model-shot/route.ts:23` (only `side === "front"` is counted, so any number of back views can be requested with any of your own storage URLs as `frontUrl`); `lib/server/rateLimit.ts:3-5` (in memory per server instance; on Vercel each instance has its own count); `ai/layout/route.ts:17` and `ai/styles/route.ts:15` (return an empty result when limited, so the user just sees nothing).
- Fix: M. Count back views too (e.g. 3 per day); move the limit to a Supabase row if the AI budget matters; return a 429 with copy ("You've used today's AI suggestions").

### [MEDIUM] M3. Proof files can be replaced after they are hashed on-chain
- Area: api / money
- Where: `api/proofs/route.ts:35` (`upsert` on `chain_id, listing_id, milestone`; no check of the milestone's state).
- What happens: the contract keeps the hash of the first proof. After `submitProof`, the creator can POST again and the app shows the new files. Anyone re-hashing the stored record would see a mismatch, but a brand reviewing in the UI sees the replacement.
- Fix: S. Read the milestone from the contract and refuse a write once a proof has been submitted.

### [MEDIUM] M4. A campaign owner can trigger the global campaign runner at will
- Area: api
- Where: `api/campaigns/[id]/route.ts:31` (`body.run` calls `runCampaigns()` for every campaign, with no rate limit).
- Fix: S. `allow(\`campaign-run:${user.did}\`, 60)` and only run that campaign.

### [MEDIUM] M5. Reduced motion is only half done
- Area: design-system
- Where: `globals.css:372-379` handles CSS animation. JS animation from `motion` outside a `MotionConfig`: `app/explore/ExploreFeed.tsx:351`, `app/campaigns/new/CampaignBuilder.tsx:161` (`LandingView` and `ListingRoom` do wrap in `MotionConfig reducedMotion="user"`; `SpotBubble` is inside `ListingRoom`).
- What happens: with "reduce motion" on, those still slide and fade.
- Fix: S. Put one `<MotionConfig reducedMotion="user">` in the root layout providers.

### [MEDIUM] M6. Hard-coded colours outside the tokens
- Area: design-system
- Where: dark policy panels use `#1A1A1C`, `#E9E7E0`, `#C9C7BF`, `#A8A69E`, `#76746C`, `#3A3A35` in `CampaignBuilder.tsx:230-246`, `CampaignView.tsx:252-259`, `OfferBuilder.tsx:185`, `OfferView.tsx:180-190`; `ExploreFeed.tsx:178` (`#4ADE80`); `NetworkSwitch.tsx:23` (`#F5B400`); `SpotBubble.tsx:176` repeats the pastels as hex. About 76 hex values in total outside the SVG art.
- Expected: tokens (`--ink`, `--muted`, `--p1..p5`, `--green`). The dark panels are intentional but should be a token or a shared class so they don't drift.
- Fix: M.

### [MEDIUM] M7. Navigation doesn't match the spec, and two pages are duplicates
- Area: ux / docs
- Where: `Sidebar.tsx:34-38` has Home, Events, Explore, Activity, Profile (5 + Create); SPEC-v2 §3 says "Four nav items in total" with Explore as the search box. `/dashboard` and `/bids` still exist as pages, but their content is the Earnings and Bids tabs of the profile (`ProfileView.tsx:194-195`); SPEC-v2 says there is no separate dashboard or bids page.
- Fix: S/M. Decide: update the spec, or redirect `/dashboard` and `/bids` to `/<me>?tab=…` and drop Explore from the sidebar.

### [LOW] L1. Smaller things
- `app/campaigns/new/page.tsx:26` hard-codes "+5% or +$5" with float maths; the contract's `minIncrementBps`/`minIncrement` can be changed in the admin Timing panel, so the estimate can drift (preview only; the contract stays the authority).

## UX review

Compared with `token2049.vanshu.fun`: it puts both sides of the outfit above the fold with each spot labelled and priced on the photo, shows "$0 raised of $9,200 · 13 of 13 spots open · sales end Sep 15", gives each spot a sentence about why it's valuable, and has one clear call to action. The Patched listing page (from the e2e screenshot) already does most of this (escrow total, countdown, spot table, perks, FAQ) and is strong. The gap is the photo: the outfit sits small in a big canvas, so the spots are hard to tell apart and the first screen is mostly text.

At most three issues per screen:

**Creator profile `/[handle]`**
1. A new creator sees "0 deliveries · $0 earned · 0 spots sponsored" under the name. Zeroes read as "nobody trusts this person". Show reach (X followers are already stored), spots open, and the next event instead; show delivery stats only once there is one. (S)
2. A visitor has no call to action. The only way into a bid is to spot the listing card. Add a primary "See live spots" / "Sponsor a spot" button next to Share when a listing is live. (S)
3. The banner is a flat colour with a faint "patched" wordmark. Let the creator's best listing photo or event cover sit there, or reuse the new `EventMark` tile style. (M)

**Listing page `/[handle]/[listingId]`**
1. The canvas is large but the outfit is small; patches are tiny. Crop the canvas to the subject (the AI already cuts the background out). (M)
2. The H1 is the generic "Walking board for you". Use the creator's headline field, or the listing title and event ("Dhruv at Token2049"). (S)
3. Show a goal line like the benchmark ("$62 of $370 · 2 of 6 spots open"); today the total is there but "spots open" is only in small print. (S)

**Event page `/e/[slug]`**
1. With one creator going, the spots grid is a single card at the far left and the live wall sits at the far right, leaving a hole in the middle. Make the live wall a row under the leaderboards when there are fewer than three cards. (S)
2. "Run by its organisers. Patched lists who's going…" is 12px grey text between the header and the stats; it reads like a footnote on the most important screen. Move it to the footer of the page. (S)
3. Stats ("1 creator going · 2 open of 6 spots · $62 bid so far") are the strongest social proof and are the least styled element. Give them the card treatment and mono numbers. (S)

**Brand side: `/campaigns/new`, `/offers/new`, bids**
1. The campaign and offer builders use a dark policy panel in both themes with hard-coded greys (M6). It is the Privy showpiece; make it a real component with tokens and a short "What Privy enforces" heading. (M)
2. Bids and sponsoring live in the profile's tabs; the wallet panel links to `?tab=bids`. A brand's first action after outbid is "Bid again" from a toast; there is no persistent "you were outbid" place besides Activity. Add a count badge on the Profile tab when outbid. (M)
3. The Privy features (auto-bid, campaigns, offers) are on three different pages with three different names. A single "Automate" entry on the listing page would make them findable in a demo. (M)
